## Testing

运行测试：
- 非 GUI 套件：`swift test`
- GUI/WebKit 套件（导出、打印、Mermaid/flow/sequence 渲染、PDF 外观）：`MD2_RUN_GUI_TESTS=1 swift test --filter MermaidOffscreenRenderingTests --filter PDFExportEndToEndVerification`

GUI 测试通过 `MD2_RUN_GUI_TESTS=1` 选择性开启：本地 `swift test` 默认会跳过，CI 的 `gui-tests` job 在每个 PR 上开启它们（见下文）。**任何改动 `Sources/MD2App/PDFExporter.swift` 或 `Sources/MD2App/DocumentPrinter.swift`（PDF 导出/打印路径）的提交，落地前必须在本地跑 GUI 套件** —— 这条路径的失败大多是静默的（深色/反转 PDF、被裁剪或消失的图），不抛错，只有 GUI 测试或人工导出能抓到。

`PDFExporter.swift` 里两行是 load-bearing，删了会静默回归（深色 PDF），改它们之前先看对应 GUI 测试：
- `hostWindow.appearance = NSAppearance(named: .aqua)` —— 强制浅色外观（守：`testPDFExporterForcesLightAppearanceOnHostWindow`、`testForcedLightAppearanceUsesDefaultMermaidTheme`）
- `printStyleScript` 里的 `img, canvas, svg:not(.diagram-mermaid svg)` 选择器 —— 保留 Mermaid 自然尺寸（守：`testNarrowMermaidKeepsNaturalSizeUnderPrintOverride`、`testWideMermaidFitsPrintableColumnUnderPrintOverride`、`testNonMermaidMediaCappedUnderPrintOverride`）

CI 的 GUI lane：`.github/workflows/pr-verify.yml` 的 `gui-tests` job 在 GitHub 的 `macos-15` runner（有登录会话和 window server）上跑 `MD2_RUN_GUI_TESTS=1 swift test --disable-swift-testing`（只跑 XCTest：GUI 门控用例必须写成 XCTest，Swift Testing 套件已在 `build-test-package` 跑过，job 里有一步会拦住读 `MD2_RUN_GUI_TESTS` 的 Swift Testing 文件），再用 `Scripts/check_test_skips.py` 拒绝 `.github/gui-expected-skips.txt` 之外的任何 skip —— 被跳过的 GUI 测试同样是绿的，不查 skip，这个 lane 什么都证明不了。新增的 `XCTSkip` 路径如果会在 runner 上触发，必须在 allowlist 里加一条（钉住测试名和 skip 原因的开头）并写明为什么 runner 跑不了，否则 CI 失败。runner 镜像已授予 Accessibility，所以 `SettingsWindowPresentationGUITests` 里需要它的 Settings 命令用例在 CI 上也会真跑。CI 只覆盖 macOS 15，开发机覆盖当前系统，两者互补，所以上面"落地前在本地跑"的要求不变。

Find/delete GUI guards: the delete-after-reveal test and the find responsiveness
benchmark in `Tests/MD2CoreTests/` are `MD2_RUN_GUI_TESTS`-gated: plain
`swift test` skips them and CI's `gui-tests` job runs them. After changing
the find/reveal/highlight path in
`Sources/MD2App/MarkdownEditorView.swift`, run
`MD2_RUN_GUI_TESTS=1 swift test --filter FindFindDeleteGUITests` locally before landing —
this path fails silently (Backspace deletes a whole word, find-mode stutter), and
only the GUI tests or manual use catch it.

Line-number guards: the editor gutter (`MarkdownSourceTextView` draw path in
`Sources/MD2App/MarkdownEditorView.swift`) and the preview gutter
(`__md2RenderLineNumbers` in `Sources/MD2App/MarkdownPreviewView.swift`) are
covered by GUI-gated suites that `swift test` skips. After changing either
surface — or the export-isolation boundary they depend on — run
`MD2_RUN_GUI_TESTS=1 swift test --filter EditorLineNumberGutterGUITests --filter LineNumberGutterGUITests`
locally before landing. The guarded failures are silent: a gutter that stops
drawing, numbers that drift from their lines after an edit, or preview digits
that leak into exported PDF/HTML. Two non-obvious constraints those tests pin
down: `NSTextView` clips its drawing to the text container, so the gutter must
re-clip to the dirty rect or its painting in the container inset is discarded;
and the clipboard/find paths must never see the digits, which is why they are CSS
generated content rather than text nodes.

Settings-window launch guard: `Sources/MD2App/MD2App.swift` declares `Settings`
as the app's only SwiftUI scene (document windows are AppKit-managed), and
SwiftUI presents an app's only scene at launch when the binary is linked below
the macOS 15 SDK — so without the `.defaultLaunchBehavior(.suppressed)` opt-out
the Settings window opens by itself on every launch, including the Finder opens
that launch the app. The macOS 15 platform floor (`Package.swift`,
`DirectLaunchBootstrap`'s generated plist, and `Scripts/package_app.sh`) is what
that API requires, and it is also what makes SwiftPM link the binary as `sdk 15`;
both layers are deliberate, and the floor must not be lowered without keeping the
opt-out. After changing launch wiring, that scene/command tree, or the Settings
window, run
`MD2_RUN_GUI_TESTS=1 swift test --filter SettingsWindowPresentationGUITests`
locally before landing. The failure is silent — a window that reappears throws
nothing. It is the repo's first multi-process GUI test (it builds and launches a
real app bundle under its own bundle identifier, never the developer's app
state), and its Settings-command cases need Accessibility trust: without it they
skip loudly rather than pass one-sided. Grant it to whatever runs `swift test`
(System Settings ▸ Privacy & Security ▸ Accessibility).

Undo-history guards: each document owns one `UndoManager` (`DocumentStore`) and
one editor text view (`MarkdownEditorSession`), which every editor re-hosts.
`NSTextView` registers undo actions whose target is the text view, unretained,
so a text view rebuilt per mode switch crashes Undo after Write → Read → Write;
and text that reaches the document outside the editor must go through the
session (`applyUndoableEdit` for checkbox toggles, `resetText` for opens and
reloads), or undo replays stale ranges — an exception, or a silent rewrite that
autosave persists. After changing the editor's view lifecycle (`makeNSView` /
`dismantleNSView`, the session), the window's undo wiring
(`MD2AppDelegate.windowWillReturnUndoManager`, `makeDocumentWindow`), or any path
that changes `DocumentStore.text` programmatically, run
`MD2_RUN_GUI_TESTS=1 swift test --filter UndoHistoryGUITests` locally before
landing (the headless `UndoHistoryTests` run in `swift test`). Constraints those
tests pin down: the session, not a coordinator, is the kept text view's
delegate, because in Read mode no coordinator exists and something must still
supply the document's undo manager (an unhosted text view has no window to fall
back to) and pass undo/redo and toggle text to the document; and a window asks
its delegate for an undo manager once and caches the answer, which is why the
document is registered before the content view is installed. Under XCTest,
SwiftUI keeps a dismantled editor's host alive, so the old crash does not
reproduce there; the guard is the assertion that a mode round trip re-hosts the
same text view.

## Skill routing

When the user's request matches an available skill, invoke it via the Skill tool. When in doubt, invoke the skill.

Key routing rules:
- Product ideas/brainstorming → invoke /office-hours
- Strategy/scope → invoke /plan-ceo-review
- Architecture → invoke /plan-eng-review
- Design system/plan review → invoke /design-consultation or /plan-design-review
- Full review pipeline → invoke /autoplan
- Bugs/errors → invoke /investigate
- QA/testing site behavior → invoke /qa or /qa-only
- Code review/diff check → invoke /review
- Visual polish → invoke /design-review
- Ship/deploy/PR → invoke /ship or /land-and-deploy
- Save progress → invoke /context-save
- Resume context → invoke /context-restore
- Author a backlog-ready spec/issue → invoke /spec
